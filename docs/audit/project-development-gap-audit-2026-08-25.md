# 项目待开发与待补充清单

审计日期：2026-08-25

审计范围：页面与路由、Server Actions、API Route、数据库模型与迁移、后台运营、异步任务、自动化测试、部署与基础设施配置。

说明：本文只列当前仍需要开发、补充、验证或落地的事项，不重复列出已确认完成的功能。

> 本文是开发前审计基线。完成后的逐项状态、验收入口和测试证据见[项目补充开发完成与验收清单](../acceptance/project-completion-acceptance-2026-08-25.md)。

## 优先级定义

- **P0**：影响生产安全、数据合规或正式上线，必须优先处理。
- **P1**：首发核心业务链路不完整，需在产品验收前补齐。
- **P2**：运营效率、体验、可观测性和长期维护能力补充。
- **外部上线项**：需要云资源、账号、法务或运维流程配合，不能只靠本地代码完成。

## 一、P0：生产和数据安全阻塞项

### 1. 正式认证与首页演示登录边界未彻底隔离

- 首页 `app/page.tsx` 仍保留 `localStorage` 本地用户和任意验证码登录；它与正式 `/login` 的短信认证并存，容易被误认为真实登录。
- 无数据库时首页会自动进入完整演示数据模式，包含演示用户、动态、活动和个人记录。
- 需要明确生产行为：生产环境首页直接进入 `/login`，或将演示入口严格限制在 `/prototype`/显式 feature flag，并在界面持续显示“本地演示、不发送短信”。
- 需要补充生产/演示模式隔离测试，确保演示身份不能访问真实账号、后台或写入正式数据。

### 2. PostgreSQL、Redis、短信、OSS 和内容安全真实链路尚未完成环境验证

- 本机缺少 `.env.local`、PostgreSQL、Redis、Docker 和真实阿里云配置。
- `pnpm test:integration` 的数据库集成用例因缺少 `DATABASE_URL` 跳过；E2E 中依赖数据库、Redis、认证、后台、真实 OSS 的场景也未执行。
- 需要建立 staging 环境并完成：迁移、种子数据、短信发送/校验、Redis 会话与限流、OSS 预签名/回调/公开读取、媒体审核、Worker 和 `/ready` 200 验证。
- 需要将真实执行结果和失败日志归档为发布证据，不能以本地 mock 结果代替。

### 3. 发布、部署、灰度、回滚和压测尚未形成真实证据链

- 当前工作区改动尚未形成新的远端 CI 成功记录。
- GitHub staging/production Environment、reviewer、Secrets、ACR 镜像 digest、Trivy 报告、Terraform plan/apply、SAE 部署、多实例版本校验均未产生本轮真实 artifact。
- k6 仅完成脚本/配置检查，尚无 staging 100 RPS 读取、5 RPS 写入和性能阈值报告。
- RDS/Tair 备份恢复、10%→50%→100% 灰度、应用回滚和迁移失败恢复尚未演练。
- 需要补齐可审计的 CI → 镜像 → 基础设施 → 部署 → 健康检查 → 压测 → 灰度 → 回滚链路。

### 4. 注销账号后的内容留存与匿名化策略不完整

- `features/admin/actions.ts` 的 `completeAccountDeletion` 会处理资料、媒体、关系、报名和帮助工单，但没有明确处理该用户已发布的 `posts`、`comments` 及其内容中的个人信息。
- 这些内容仍保留作者外键和正文，仅因用户状态变为 deleted 而不再正常出现在公开查询中，不能替代可审计的删除、匿名化或法定留存策略。
- 举报、申诉、审核记录、活动发起记录等关联数据也需要明确哪些保留、哪些匿名化、保留期限和访问权限。
- 需要补充数据保留矩阵、事务/异步清理策略、失败重试和注销完成后的数据库断言/E2E。

### 5. 头像发布链路存在审核状态和对象键不一致风险

- `features/account/actions.ts` 的 `updateProfileAvatar` 接受 `uploaded` 状态，并把 `originalKey` 写入 `profiles.avatarKey`；原图对象与审核后的 `publicKey` 不是同一条安全发布链路。
- 正式 `/me` 上传组件只提示“审核通过后自动更新”，没有基于 `mediaId` 的审核状态查询、失败反馈和页面刷新；首页又使用另一套即时绑定逻辑。
- 需要统一所有入口为“上传 → 回调 → 审核通过 → 绑定 approved publicKey → 展示”的流程，禁止未审核原图直接进入公开资料，并补充拒绝、重复上传、Worker 延迟和私有 OSS 访问测试。

## 二、P1：首发核心业务链路缺口

### 6. 机构申请没有形成完整的成员生命周期

- 数据库只有 `organizations` 和 `organization_applications`，没有机构成员/加入关系表或等价授权模型。
- `reviewApplication` 审批通过后只更新申请状态、发送通知和写审计，不会建立机构成员关系，也不会维护 `organizations.memberCount`。
- 申请使用机构与用户唯一索引，用户被拒绝后没有撤回、重新申请或重新提交入口。
- 正式产品路由没有机构目录和机构详情页，主要入口仍在首页原型的内嵌机构视图。
- 需要补充机构目录/详情、申请状态与撤回/重申、审批通过后的成员关系、成员数维护、权限边界、通知深链和完整 E2E。

### 7. 帮助中心和工单闭环不完整

- `/help` 的 FAQ 是前端硬编码，后台没有 FAQ 分类、搜索内容、版本或编辑发布能力。
- `resolveHelpTicket` 只更新工单状态并写审计，没有向提交人发送 UI 承诺中的站内通知。
- 用户个人中心没有帮助工单列表、处理中状态、处理结果和后续追问/关闭/重开入口；`/me/applications` 只展示机构申请。
- 匿名工单提交没有独立的频率限制、重复提交控制或反滥用策略。
- 需要补充工单状态流转、负责人/处理中、解决通知、用户查询页、FAQ 管理和帮助表单安全限制，并增加“用户提交 → 后台处理 → 用户收到通知”的 E2E。

### 8. 活动详情与报名后运营能力不完整

- `PublicActivity` 和正式活动详情页只读取摘要、开始日期、地点、容量和报名数，没有展示数据库中的 `details`、结束时间、发起人、取消/结束状态等完整信息。
- 数据模型包含 `attended`、`no_show`，但没有管理员/组织者签到、缺席标记和用户侧活动结果展示。
- 详情页的报名/取消按钮没有充分按“已满、已取消、已结束、已过期”展示状态和操作边界；活动列表也缺少城市筛选与分页。
- 需要补充活动完整详情、状态驱动的报名控制、结束后签到/缺席管理、组织者视图、通知深链和状态迁移测试。

### 9. 正式城市页没有完成成员、机构和政策分区

- `app/(product)/cities/[citySlug]/page.tsx` 的“成员”标签只跳到一个说明卡片，没有成员目录、搜索、排序或分页。
- 正式城市页只有动态流；“活动”链接跳到全国活动页，机构和政策只在首页原型中提供城市内视图。
- 城市动态固定读取前 30 条，没有加载更多、游标分页、话题/内容筛选。
- 需要补充正式城市内的成员目录、活动/机构/政策分区或清晰的城市筛选，以及动态分页和空状态/错误状态。

### 10. 正式成员主页资料维度不足

- `getPublicMember` 只返回基本资料和最多 30 条公开动态。
- 正式成员页没有关注者/关注中数量、加入的城市、参与/发起的活动、公开贡献信息或更多动态加载。
- 需要根据首发范围补充成员统计、城市与活动关系、分页/加载更多、隐私可见性和被屏蔽后的展示规则。

### 11. 个人中心的账号功能还未完全闭环

- `/me` 已读取 `avatarKey`，但页面仍只展示昵称首字母，没有展示已审核头像。
- “我的申请”只包含机构申请，不包含帮助工单；“我的关注”的描述包含城市，但实际只查询成员关注。
- 通知只支持“全部标为已读”，没有单条已读、目标内容跳转、通知 payload 深链和未读筛选。
- 会话页缺少过期/撤销会话清理、设备信息完善和风险提示；申诉页缺少目标详情、处理时间线和补充材料/重新提交能力。
- 需要补充以上入口、状态展示、深链和相应权限/回归测试。

### 12. 政策内容只有公开读取，没有运营管理闭环

- `policies` 有来源、发布机关、文号、生效日期等字段，但后台 `content` 只管理知识和洞察，没有政策新增、编辑、审核、发布、隐藏、废止或版本管理。
- `sourceUrl` 目前只有唯一约束，没有官方来源域名校验、来源可用性检查、抓取时间或修订/失效标识。
- 正式政策列表没有城市筛选；城市政策入口和全局政策数据之间未形成统一的运营维护流程。
- 需要补充政策 CMS、来源校验、版本/废止状态、审核审计、城市归属、缓存失效和来源异常告警。

### 13. 知识与 AI 洞察内容模型和展示能力偏原型化

- 知识和洞察正文在详情页都作为单个 `<p>` 输出，不支持结构化段落、标题、列表、引用、链接或安全 Markdown/rich text。
- 内容表没有作者展示、更新时间、引用来源、原始链接、事实核验状态等字段；AI 洞察列表使用硬编码的“DAILY · 2026”和“今日”文案。
- AI 洞察缺少来源追溯、生成/编辑责任边界、更新时间和失效处理展示。
- 需要补充内容编辑模型、富文本安全渲染、作者/更新时间/来源字段、AI 内容溯源和前台事实/风险提示。

### 14. 正式产品导航和 SEO 收录策略不完整

- 主导航没有政策入口；个人中心的通知、申请、申诉、会话等功能隐藏在二级页面，正式用户不易发现。
- `app/sitemap.ts` 收录城市、活动、知识和洞察，但没有公开政策详情、动态详情和成员主页的动态 URL；这些路径又没有统一说明是否应被搜索引擎收录。
- 需要明确用户生成内容和成员主页的 `index/noindex` 策略，补齐应收录的政策/公开内容 URL，补充 canonical、更新时间和删除内容的 sitemap 清理。

## 三、P2：运营、工程质量与长期维护补充项

### 15. 后台运营台仍是固定列表和低效操作模式

- 用户、动态、评论、媒体、活动、工单、审计和死信列表大量使用固定 `limit`，没有分页、筛选、搜索、排序、批量操作、导出或详情页。
- 城市管理员和角色分配依赖 `window.prompt` 输入 UUID，缺少可搜索用户选择器、变更前确认和结果回显。
- 举报和申诉按城市范围过滤时存在逐条查询的 N+1 结构，数据量上升后会影响后台性能。
- 需要补充运营查询条件、游标分页、批量审核、用户/城市选择器、详情与操作时间线，并优化作用域查询。

### 16. 互动、评论和话题内容缺少持续运营能力

- 话题字段已写入动态，但正式动态详情和城市页没有话题展示、话题聚合页或按话题筛选。
- 评论虽然支持 `parentId`，前台列表仍是扁平展示，没有回复层级、被回复对象或折叠/加载更多。
- 分享、点赞、关注等动作缺少统一的失败重试、状态回滚和操作结果可见性验证。
- 需要补充内容发现、评论层级、长列表性能和互动失败体验。

### 17. 真实媒体生产能力和对象生命周期仍需落地

- 真实 OSS 预签名、回调、内容安全审核、公开 CDN/私有回源、跨域配置尚未在 staging 完成验证。
- 原始上传对象、审核拒绝对象、公开对象的清理、生命周期、重试和异常孤儿文件处理策略未形成可执行任务。
- 需要补充图片/视频元数据、缩略图/转码需求评估、对象清理任务、私有回源验证和媒体成本监控。

### 18. 自动化测试覆盖仍集中在领域层和公开页面

- 当前覆盖率命令只统计 `server/domain/**/*.ts` 和 `lib/phone.ts`，不能代表全仓库覆盖率。
- 需要新增或接通真实数据库/Redis 的集成用例：机构申请与审批、帮助工单通知、注销完成与匿名化、死信重放/忽略、媒体审核公开读取。
- 需要增加 390px 精确视口、正式详情页/登录后页面/后台页面的可访问性、键盘焦点和长内容回归。
- 需要补充完整 SQL/对象注入字典、超大请求体、高频工单/验证码滥用和权限 IDOR 的独立安全测试。
- 需要完成真实迁移回滚/恢复演练，而不仅是迁移连续性检查。

### 19. 帮助、互动和公开接口需要更细的反滥用策略

- 帮助工单目前没有用户/IP 维度的频率限制、重复问题合并或人工验证。
- 互动、举报、评论和媒体预签名虽然有基础校验，但缺少统一的高频调用监控、封禁策略、请求体上限验证和异常告警证据。
- 需要明确各接口的限流维度、配额、错误码、审计字段和压测/安全验收标准。

### 20. 可观测性和告警尚未形成可运营系统

- `instrumentation.ts` 只有基础 OTel 注册和错误日志；尚无可验证的请求、业务、Worker、短信、OSS、数据库和队列指标看板。
- SLS/ARMS/OTLP 的真实接入、告警联系人、SLO、成本告警、死信告警和告警演练尚未产生环境证据。
- 需要补充指标命名、trace/log 关联、关键业务告警、值班责任、告警降噪和故障演练。

### 21. 多实例缓存和数据一致性方案需要明确

- 当前未引入自定义远端 cache handler；如果后续启用 ISR、Cache Components 或更积极的页面缓存，需要补充 Tair/远端缓存和跨实例失效机制。
- 需要明确动态内容、政策、活动、城市计数和用户通知的缓存 TTL、失效触发点、发布后可见时延和多实例一致性测试。

## 四、外部上线前必须补齐的事项

### 22. 云资源、备案和密钥配置

- 生产域名、HTTPS 证书、ALB/Ingress、WAF、CDN/DCDN、OSS 私有回源、RDS、Tair、SAE、SLS/ARMS 尚未完成真实配置与验收。
- Terraform 示例中的 `REPLACE_ME`、示例域名、告警联系人、成本告警和私有回源开关不能作为上线值。
- 短信签名/模板、内容安全服务、媒体域名、ICP/公安备案和生产密钥轮换流程尚未完成。

### 23. 法律、隐私与数据治理定稿

- 服务条款、隐私政策、风险提示、内容治理和账号注销说明仍需要最终法务确认和版本发布流程。
- 需要补充个人信息字段清单、处理目的、保存期限、第三方服务清单、注销/导出/更正机制和客服响应承诺。

### 24. 备份、恢复和运营值班机制

- RDS/Tair 备份保留、恢复点目标、恢复时间目标、隔离恢复环境、演练频率和责任人尚未形成实测记录。
- 需要补充生产值班、故障升级、死信处理、短信/OSS 故障降级、数据恢复和发布回滚手册的实际演练记录。

## 建议实施顺序

1. **先处理 P0**：认证边界、真实 staging 依赖、注销数据策略、头像安全链路。
2. **再补 P1 核心闭环**：机构、工单、活动、城市/成员、个人中心、政策和内容运营。
3. **随后补 P2 工程能力**：后台效率、自动化、安全、可观测性、缓存和媒体生命周期。
4. **最后完成外部上线项**：云资源、备案、法务、备份恢复、灰度与回滚证据。
